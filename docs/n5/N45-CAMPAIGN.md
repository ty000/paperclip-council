## Operator-assisted campaign recipe

Before any launch obtain fresh explicit authorization for exact source/host SHAs, actual model/effort, proposed 2M reservation per run and 30M period allowance, repository/base/branch and permitted publication effects. Model recommendation is Sol/medium, source `/home/davy-lp/.codex/shared/model-selection/model-effort-mapping.md` dated 2026-09-05. Actual model availability remains unobserved. The proposed maximum is 15 runs; nominal is 9, a genuine correction before publication can reach 14 and after publication 15. G4 admission/reservations are not a hard cap on provider consumption. Stop on unknown usage, failed run, unexpected extra wake or an exhausted envelope; no retry or new period.

1. Recreate the temporary preparation in a fresh isolated instance/company/project/clone. Keep the installed local instance untouched. Read back the six configured agents, adapter profiles, instructions, plan revision, fixed rosters and envelope. Verify provider and projected GitHub capabilities before waking anyone. Preserve the instance for the explicitly authorized operator session; the `prepare` command itself always cleans up.
2. Enable on-demand wake only for the required six campaign identities. N1 lead/backend/frontend use `codex_local` CLI and real commits. Activate the mission and call existing owner `start-lead` with a fresh command/reservation, exact version and 2M units. The lead refines the native plan, agrees the pure presentation interface, then uses existing `plan`, `materialize`, `dispatch`, `reconcile-usage`, and `publish`. It serializes backend and frontend. One bounded terminal wait per child is allowed; the lead run stays occupied and counted during that wait. Do not spend repeated model turns polling. Contributors own distinct paths, commit, record their contribution and finish. The lead integrates, runs canonical checks, creates/uploads a self-contained base/candidate Git bundle, publishes it and finishes. No artificial defect or fixture contribution.
3. Settle all three exact N1 runs using existing owner reconciliation, preserving unknown reservations. PATCH the same lead agent to `paperclip_runner` with the selected Codex profile and read back adapter/config. Do not change its identity, company or period. Configure N5 authority before acceptance: native plan key/revision/hash, lead planner/orchestrator/integrator, independent QA, exact publisher agent, Council repository/main/isolated head, draft policy and 2M publisher reservation. Authority remains unchanged during later plan rebinding.
4. Call existing owner `start-review` with the current candidate, same allowance and Development/Quality required slots. Existing N2/N3 commands own transmission, specialist dispatch/opinions, independent synthesis/decision, actual correction when justified, exact acceptance and usage settlement. Native-run agents use the catalogued `POST /api/plugins/tools/execute`, tool `private.paperclip-council:mission-command`, `parameters: {operation: "command" | "decision", body: <existing agent command>}` and their own native gateway runContext. Never pass identity/issue overrides inside parameters. These gateway commands apply to ordinary source/specialist/publisher runs. The native reviewer instead reads its one active packet, resolves its card and finishes the exact JSON summary. The dedicated lead hold/release is performed by the owner as specified in the readback contract; no extra reviewer run is added.
5. Existing terminal reconciliation admits a distinct publisher run only after independent acceptance and all usage is settled. The publisher inspects and claims its persisted N5 intent before git/gh, verifies exact candidate/repository/refs, creates at most one PR, registers its attributed work product and native delivery document, refreshes external objects and reports checks/reviews with their actual provenance. Unknown effect is not permission to create again. Finish on pending checks or native refresh backoff; operator refresh/reconcile handles later observations without an idle model. A real post-acceptance correction uses the existing one-correction continuation and same PR, never a reset or replacement review pipeline.
6. The runtime initially serves the base Council UI. After acceptance and settlement, the operator builds the exact accepted candidate and installs/upgrades that build **only in this temporary instance**, reads back its installed artifact/source identity, then observes the actual Delivery panel in a browser against the same native mission. A screenshot of the base UI is not evidence of the produced panel. Record actual criterion observations; no synthetic screenshot counts as real UI proof. Do not claim campaign/UI readiness until this step and exact PR/readbacks are complete.
7. Record all run IDs/statuses/usage, reservations, native plan revisions, N3 opinions, independent verdicts, exact candidate and PR SHA/ref/readbacks, UI build identity and observed evidence. Stop the owned instance and remove its disposable resources. Preserve the evidence and report whole command status alongside scenario results.

The backend contribution owns `src/delivery-presentation.ts` and `tests/delivery-presentation.spec.ts`; frontend owns `src/ui/index.tsx`. Lead chooses the concrete interface and integration plan. These files are left for the real mission. Specialist agents advise; the independent Council reviewer alone decides acceptance.
