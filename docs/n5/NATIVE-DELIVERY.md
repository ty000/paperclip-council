# N5 delivery and bounded continuation

This slice connects the merged N1–N3 mission to an authorized publisher. It is not M1/provider qualification. The first real representative mission remains the Missions Delivery panel: complementary backend projection/tests and frontend work, a shared planner/orchestrator/integration lead, Development and Quality specialists, and an independent final reviewer. That UI is deliberately left to that mission.

The current `ordinary-cli-v1` profile uses authenticated plugin APIs and ordinary `codex_local` CLI tasks throughout review, correction and publication. Historical runner missions retain their persisted protocol. Enable it through the [ordinary profile](../n3/ORDINARY-CLI-REVIEW.md); the lead, specialists, Council and publisher remain CLI agents. No runner switch or native completion receipt is required.

## Ownership and native boundary

Council owns the mission aggregate, mandate binding, authority, one-shot intent and attributed observations. The pinned Paperclip host `61b3fd57a695614dc4a37e2303f426a34a9795cf` owns revisioned documents, child issues/workspace inheritance, run identities, costs, work products, external-object detection/refresh and GitHub snapshots. The host experimental setting `enableExternalObjects` must be enabled on the selected instance; the qualification changes it only in its isolated temporary instance. Its default is false, in which case native external-object lists are empty. No host writes, migration, new table, scheduler or generic GitHub service are introduced. Git/gh in the publisher's existing adapter is the publication effect boundary. Network, credentials, repository access, gh availability and actual model behavior require a fresh real-runtime preflight before LIVE.

## Native plan and initial authority

Write a native document with key `plan` using `write_document` or `PUT /api/issues/:id/documents/plan`. Its Markdown body contains one JSON object with `missionId`, `mandateHash` (Council canonical payload hash of the mandate), `plannerAgentId`, `orchestratorAgentId`, `integrationLeadAgentId`, `qaAgentId` and `work`. Each of at least two complementary work entries contains `assigneeAgentId`, `sourceRefs`, `ownedPaths`, `dependencies`, `evidenceRefs`, `skills` and `interface`. These references consume prepared work rather than recreate an upstream backlog. Read the current document/revision and use `baseRevisionId` for updates. Never put credentials in documents.

The mission owner calls the existing mission commands route with `configure-delivery`, `commandId`, `expectedVersion`, `planRevisionId`, `publisherAgentId`, `repository` (`owner/repo`), `baseRef` and `headRef`. Configuration explicitly authorizes one initial PR creation and, within the existing single correction limit, update of that same PR for the independently accepted candidate on these refs. The plan is read from native storage and its exact revision/hash retained; Council does not store a second plan body. Reconfiguration before admission supports replanning within the mandate. An admitted intent cannot be replaced by a new key or authority.

The terminal N2 event admits the publisher only after exact Council acceptance and all review/source accounting. Ordinary missions use the candidate-bound Council report and terminal CLI usage; historical runner missions use [native verdict readback](NATIVE-REVIEW-READBACK.md). In the dedicated-lead assisted profile, an owner restores the held lead wake policy before admission when that lead is also publisher. Configuration may precede acceptance. For a mission already accepted before configuration, the owner can use `reconcile-delivery`; this recovery uses the persisted authority. One native child inherits the root execution workspace and receives its own G4 reservation. Planning, orchestration and integration may share a lead; independent acceptance remains the final reviewer's responsibility.

## Publisher instructions

1. Use the publisher child assignment and exact active run. For ordinary CLI, POST `n5-inspect` with `missionId` to `/api/plugins/private.paperclip-council/api/issues/:childId/council/commands`, using the agent run JWT in `Authorization: Bearer` and `X-Paperclip-Run-Id`. Generated child descriptions carry the full command contract. Obtain `expectedVersion` from fresh inspection and a fresh UUID per logical mutation; replay uncertain responses with the identical key/body. Gateway permission is not assumed.
2. Inspect the native plan, accepted submission, repository remote and base/head. Verify `git rev-parse HEAD`, the target branch and remote candidate against the accepted commit; check gh authentication and permission without disclosing tokens. Stop if the worktree/ref/candidate differs. A role label alone never grants publication authority.
3. Call `n5-claim-publication` with `missionId`, `commandId`, `expectedVersion`. Only an applied response with `effectPermission: execute` authorizes the single specified `operation` (`create` or `update`). The durable state becomes `unknown` before the external effect. A replay returns `effectPermission: none`. A lost response or timeout is not permission to retry create.
4. Use the existing git/gh terminal tool for the authorized target. For create require the remote head absent and use an explicit empty lease. For amended V2 require local HEAD==acceptedV2 and remote head==previous observed V1, then push with `--force-with-lease=refs/heads/<head>:<oldV1>` and exact V2 source. Never blind force, implicit lease or retry a mismatched head. See the [ordinary campaign recipe](ORDINARY-CAMPAIGN.md) for exact commands. A draft is allowed as an observed PR but never counts as ready. No merge/deploy is authorized by this contract.
5. On the publisher child, create the native `pull_request` work product with `provider: github`, the canonical URL and exact `createdByRunId`. Write the native `delivery` document with JSON `{ "intentId": "...", "url": "https://github.com/owner/repo/pull/123", "link": "<https://github.com/owner/repo/pull/123>" }`. The `link` autolink delimiters are required for the pinned native URL detector: a bare URL inside JSON captures trailing quotes as part of the URL. Select the detected `github` object, not a generic `url` entry. A work product alone does not create an external-object mention.
6. Read `/api/issues/:childId/external-objects`, then refresh the exact object with authenticated `POST /api/issues/:childId/external-objects/refresh`. Inspect `refreshed` and `reason`, not HTTP 200 alone: the host returns `backoff` until `nextRefreshAt` (GitHub TTL 300 seconds), with no public force option. The stored observation is explicitly a dated snapshot, not an instantaneous remote guarantee. Council reads only; it does not impersonate the publisher for this mutation.
7. Call `n5-observe-delivery`. Council independently reads the document, work products and external objects. The native snapshot must be fresh and resolved after the intent, belong to the exact repository/PR/document and contain the actual SHA/base/head. Missing SHA is unknown, never filled from the request. Work-product branch fields alone are not head proof.
8. Optionally supply `checks` and `reviews`, each with `headSha`, explicit `state` and nonempty `evidenceRefs` pointing to the tool results. Checks states: `unknown`, `pending`, `passed`, `failed`; review states: `unknown`, `pending`, `approved`, `changes_requested`. These are authenticated publisher observations, explicitly distinct from native GitHub head observations and Council acceptance. Missing observations cannot be ready.
9. Finish the run normally without setting the issue done. For ordinary missions the plugin sets the publisher blocked after the effect claim, then closes it only after exact terminal CLI usage settles its own reservation. Readiness requires this settlement, even when the PR and checks are already visible; `reconcile-delivery` is the supported owner recovery if terminal telemetry was delayed. Unknown usage retains exposure.

After the publisher finishes, the owner may refresh the native external object and call `reconcile-delivery` to deterministically reread the plan, delivery document, work product and GitHub snapshot. Optional `checks`/`reviews` on this command are explicitly attributed to that authenticated owner, with no fabricated agent run. Failed native readback removes readiness. This path admits no extra model run and never repeats GitHub creation.

The mission read route exposes `n5`: referenced plan, responsibilities, authority, intent/run/child, accepted submission, native PR snapshot, separately attributed checks/reviews, readiness and next actor. Native readback readiness expires after five minutes. This backend inspection is the intended input to the future Delivery UI.

## Post-acceptance correction and plan rebinding

The owner can call `request-delivery-correction` with `commandId`, `expectedVersion`, `reservationId`, a substantive `reason` and bounded `criteria`. This requires an accepted first N2 round with terminal accounting, an observed open PR and a settled publisher. It consumes the mission's existing correction ordinal 1. An already consumed correction is refused: no reset, child review pipeline, new period or higher limit is inferred. The old application, plan and publication are retained under `n5.continuation`; the original N2 submission/round/verdict remain immutable.

The response persists the correction and reservation before returning a one-shot `nativeAction`: the same authenticated owner executes `PATCH /api/issues/:rootId` with `resume: true` and the supplied comment. **This resume is human-assisted.** A user action may chain both HTTP calls; no additional approval per later run is required. A replay grants no permission. If a response is uncertain, inspect native state before recovery; do not issue a new key or another wake. The public REST route owns workspace reopening and native wake; Council does not use an SDK status write to bypass it or borrow a reviewer credential.

For ordinary missions, Council persists the reserved root correction task and appends the request reason, criteria and API instructions to the actual root description before returning that action. The resumed lead first calls `ordinary-inspect`, which binds the exact owner-resume run by public identity and resume intent. It reads the post-publication criteria (V1 Council approval is historical), updates the plan with `baseRevisionId` and calls `n5-rebind-plan` when needed, then uses existing `prepare-resubmission`. Preserve both contribution commits and base; amend the single integration commit to a distinct V2. Historical runner missions bind through their native N2 `inspect`. This appends N2 round 2, plus a fresh N3 opinion round when configured. Every new run reserves and settles within the same company, period and envelope; continuation runs carry correction ordinal 1. Only new independent Council acceptance with complete accounting admits the update publisher. The publisher's new one-shot intent has `operation: update` and the original `targetUrl`; use git/gh to push the accepted commit to the unchanged authorized head and update that same PR. Create is forbidden for this operation. New work-product/document attribution and a native snapshot resolved after this update intent are required; an old TTL snapshot cannot prove the changed head. The publisher can finish while refresh is on backoff; the owner refresh/readback path then completes observation without an idle model.

An admitted active root integration lead may update the native `plan` document with `baseRevisionId`, then call `n5-rebind-plan` with `commandId`, `expectedVersion`, `planRevisionId` and `reason`. Council validates exact admitted run, current native revision, unchanged mandate and delegated role identities, records the previous plan reference, and preserves all publisher/repository/base/head authority. It never copies the plan body into a new store.

## Deterministic qualification

The current ordinary installed scenario is:

```sh
pnpm build
COUNCIL_ORDINARY_DELIVERY=1 node_modules/.bin/tsx tests/functional/ordinary-installed.ts artifacts/n5-ordinary-installed-<unique-name>.json
```

It executes twelve real CLI runs from a real owner-assisted N1 prerequisite, accepts V1 directly, publishes through a simulated GitHub transport, resumes the same root once through the public owner route, rebinds the plan, accepts a real Git V2 and updates the same simulated PR. All reservations settle via public per-run usage. The host's real 300-second refresh backoff is observed; one later owner refresh/reconciliation completes readiness without another model run. The fixture supplies model text, usage and GitHub effects/transport; auth, installed commands, admission, heartbeat, Git, native documents/work products/refresh and final readbacks are real. See [qualification report](../reviews/n5-ordinary/REPORT.md). This is not LIVE publication, model judgment, UI completion or N6.

The following runner recipe is historical; its launcher is not the ordinary launcher:


Run canonical checks with `node scripts/ci/run-checks.mjs`. Installed qualification extends the existing native N3 harness with one publisher run. Use `COUNCIL_N5_NATIVE_LIFECYCLE=1 COUNCIL_N3_NATIVE_LIFECYCLE=1`, the explicit clean pinned host and `COUNCIL_N2_NATIVE_HOST_COMMIT`, then `node scripts/qualification/run-n2-native-lifecycle.mjs`. Only N1 prerequisite records, model contents/usage and the explicitly labelled GitHub create/transport are simulated. Native admission, runs, finalizers, costs, document revisions, work products, external-object detection/refresh/storage and Council commands remain real. The proof must preserve fixture limits and exact candidate identity; it does not establish real GitHub rights, network or credential scopes.

For the continuation scenario add `COUNCIL_N5_CONTINUATION=1`. It approves V1, requests a deterministic post-publication correction, resumes the same root through owner REST, rebinds the plan, obtains fresh N3 opinions and independent N2 V2 acceptance, then updates the same fake PR. The shared-workspace fixture proves the public resume route, not reconstruction of a closed isolated worktree. This remains provider-free; real model quality and git/gh effects require a separately authorized campaign.
