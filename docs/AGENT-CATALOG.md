Preparation covers Executor, Generalist Reviewer, Development Reviewer, Architecture Reviewer, UX and Accessibility Reviewer, Product Reviewer, Quality Reviewer, Security Reviewer and Operations Reviewer; a mission still selects only the responsibilities it needs.

## 1. Starting recommendation and evidence status

V1 includes H1, H2, implementation orchestration through a PR and multi-mission project coordination (PRD C01–C11, C16–C23). The two-agent path is the first implementation slice, not the release boundary. Owners compose execution teams and councils from existing Paperclip agents; a mission pins their revisions. Specialists, facilitation and bounded appeal are used only when relevant. Memory stewardship remains deferred. [V1 scope](V1-SCOPE.md) defines the lifecycle and [TAD](TAD.md) defines enforcement, dispatch and persistence.

Start the H1 foundation with **one Executor and one distinct Generalist Reviewer**, selected by the operator from suitable existing Paperclip agents. These are two agent identities, not two prompts on the same identity. The reviewer owns the delegated final verdict for this bounded workflow; the owner retains reserved decisions. A second human approval is not required for every compliant result. A specialist or appeal is added only for a consequential question the ordinary review cannot resolve.

This is proportionate to [PRD C01–C09 and §6.1](PRD.md#6-council-model-and-authority) and [roadmap H1–H2](ROADMAP.md#3-h1--useful-review-and-acceptance). A single Generalist Reviewer may use several perspectives but does not demonstrate a multidisciplinary council. Separate identities do not establish independent reasoning or superior quality; those claims need evaluation.

The integration review started from Council PRD 0.1 at `67f79f3375ab1fb8c2155cabfb80599e39a7effa` and Paperclip `61b3fd57a695614dc4a37e2303f426a34a9795cf`, including the latter's local prototype/reports and modified lockfile. This catalogue now accompanies PRD 0.5; the earlier integration review remains historical. That reviewed documentary revision contained no implementation. The TAD now records separate extraction and manifest-gate commits; neither proves the broader V1. Public source links are pinned to the reviewed Paperclip commit; unpublished local evidence is identified separately in section 9.

### 2.2 Authentication and access

There are three different authentication relationships:

1. **Codex model access:** propose the owner's WSL-native ChatGPT/Codex subscription login. Do not configure a separately billed API key, copy secrets into instructions, or choose an external `CODEX_HOME` implicitly. Paperclip supports seeding managed Codex homes from host authentication; newly managed homes are not evidence of a separate subscription or independent model. A configured API credential can take precedence, so inspect the non-secret effective authentication mode during later authorized setup. Preserve the platform's empty `OPENAI_API_KEY` inheritance guard; no raw authentication file is required in a review report. [Home selection/auth launch checks, lines 659–733](https://github.com/paperclipai/paperclip/blob/61b3fd57a695614dc4a37e2303f426a34a9795cf/packages/adapters/codex-local/src/server/execute.ts#L659), [auth precedence, lines 26–45](https://github.com/paperclipai/paperclip/blob/61b3fd57a695614dc4a37e2303f426a34a9795cf/packages/adapters/codex-local/src/server/auth-precedence.ts#L26), [adapter isolation notes, lines 169–170](https://github.com/paperclipai/paperclip/blob/61b3fd57a695614dc4a37e2303f426a34a9795cf/packages/adapters/codex-local/src/index.ts#L169).
2. **Agent-to-Paperclip calls:** native local runs receive Paperclip identity/run context and a short-lived run JWT. Mutations carry the run ID for attribution. Neither this JWT nor an API key belongs in the catalogue or prompts. [Native skill, lines 18–28](https://github.com/paperclipai/paperclip/blob/61b3fd57a695614dc4a37e2303f426a34a9795cf/skills/paperclip/SKILL.md#L18).
3. **Prototype plugin-to-Paperclip calls:** the worker resolves a dedicated standard Council agent key from a native `secret_ref` and forwards the current run ID to the public issue API. This is a trusted integration using the agent's normal authority, not a review-only credential. The TAD should retain this as the historically qualified candidate or justify a supported replacement that preserves actor/run attribution. [Local E3: Prototype README, lines 3–10 and 73–102](#9-source-baseline-and-evidence-availability), [Local E4: adapter, lines 63–89](#9-source-baseline-and-evidence-availability).

Executor access should cover only the assigned repository/workspace, allowed edits, required tests and Paperclip handoff. Reviewer access should cover the identified result, relevant source/evidence and authorized verification, plus its review decision path. The proposed reviewer does not edit the candidate to make its own verdict pass. A prompt restriction is behavioral; `workspace-write` is still technically writable. If an enforced read-only workspace, restricted network or separate credential boundary is required, the TAD must choose and qualify it. The adapter exposes Linux filesystem/network confinement options, but their prerequisites and operation were not verified here.

Do not infer task-assignment denial from `canCreateAgents: false`, a title, or a custom permission property: native creation also grants task assignment, and the effective permission calculation has separate sources. See [default task grant, lines 1732–1745](https://github.com/paperclipai/paperclip/blob/61b3fd57a695614dc4a37e2303f426a34a9795cf/server/src/routes/agents.ts#L1732) and [permission update, lines 4943–4999](https://github.com/paperclipai/paperclip/blob/61b3fd57a695614dc4a37e2303f426a34a9795cf/server/src/routes/agents.ts#L4943). Skills provide procedures, not tools, tokens, filesystem boundaries, or rights.

### 2.3 Initial owner mandate — preserved in full

This is Davy's initial single-owner profile, not a universal Council policy. Every profile consumes the current mandate; no role or skill may weaken it. The authoritative text remains [PRD §6](PRD.md#6-council-model-and-authority).

| Situation | Required decision |
| --- | --- |
| Several solutions satisfy the need and authorized limits | The reviewer/council may choose the technical approach and preserve its rationale. |
| A correction restores a validated user journey | It may be accepted within all other limits. |
| Important product change, new requirement, relaxed criterion, changed priority/success definition, or user commitment outside a delegated trade-off | Owner decision before application. |
| Majority usage improves while minority usage degrades | Delegated only while essential uses remain possible and all other limits hold; majority means usage, not screen count or a vote. |
| An essential journey becomes impossible, even for a minority | Owner decision required. |
| A degradation leaves the complete journey's p95 **strictly below 30 seconds for each affected group** | The trade-off may be delegated under the preceding conditions; the duration multiplier adds no limit. |
| That p95 is **30 seconds or greater** for an affected group | Owner decision required. Improving an already long journey is not, by itself, a degradation. |
| Infrastructure changes affect costs, **in either direction** | Prior owner decision, even inside an authorized budget envelope. |
| A new launch cannot reserve both its task allowance and the shared-period allowance, or available budget/remaining exposure is unknown | Do not launch. Corrections, appeals and resumption consume the same envelope; unknown/unpriced usage is never zero. Work already committed can still overrun, so reservation is not an absolute provider-charge guarantee. |

The p95 includes waiting in the background until a usable result is available. Representative trials may suffice only with explicit population, relevance and uncertainty. If an essential use or trade-off is decisively uncertain, a proportionate investigation precedes escalation. A follow-up does not authorize an out-of-mandate trade-off. Silence never approves anything; only dependent work waits. An owner override must remain identifiable as an owner action. Internal acceptance never authorizes an external merge, deployment, publication or expenditure on its own.

The native stage does not calculate these product facts. The reviewer checks them and the plugin/TAD must define the application guard and evidence of any reserved owner decision. A `human_only` native interaction/appropriate approval path and deliberate continuation policy are candidates; the interaction's open default is inappropriate for an owner-reserved choice. No active policy is changed here.

## 3. H1 startup profiles

### 3.1 Executor

**Mission and defended result.** Produce a useful, verifiable answer to one bounded request: a bug fix, simple feature, improvement or investigation. Integrate its own changes and explain the evidence for the owner's criteria. The result is a submission for separate review, not self-acceptance or a declaration that a larger product objective has been achieved.

**Required inputs.** Current issue and mandate; criteria and protected journeys; allowed workspace/write scope; result identity convention; relevant source and prior decisions; test/verification access; request and period limits; the selected reviewer and correction history. Missing decisive input produces a focused request or bounded investigation, not an invented product decision.

**Trigger and stopping condition.** Start on native assignment/wake with actionable authorized work. Acquire the execution checkout when required. Stop after a complete identified submission and a confirmed review handoff, after a targeted correction and resubmission, or at an explicit resumable blocker/owner-decision wait. On correction, retrieve the unchanged mandate and prior evidence before changing only what addresses the finding. Do not continue editing a submitted candidate silently.

**Observable output.** Identified result revision/content, accessible work products, criterion-to-evidence summary, relevant checks and limits, remaining follow-up, and a next actor. A changed result receives a new identity. Use native artifact/work-product procedures where applicable; a private filesystem path alone is not an inspectable handoff. See [native skill, lines 118–174](https://github.com/paperclipai/paperclip/blob/61b3fd57a695614dc4a37e2303f426a34a9795cf/skills/paperclip/SKILL.md#L118).

**Engine and access.** Shared contract: `codex_local`, explicit `cli`, WSL, proposed `gpt-5.6-sol` / `medium`, subscription authentication, bypass explicitly false. Native `role: "engineer"`, title `Software Executor`; a non-coding investigation may use `general` when the operator selects an appropriate existing agent. `capabilities` describes bounded execution and evidence production. Required tools are repository inspection/editing and task-relevant verification; GitHub/browser/provider access is conditional, not granted by the role. Budget and effective environment remain to be selected, not inferred from the historical demo.

**Skills.** S1 `paperclip` is required as the native coordination procedure and source-supported automatic runtime skill. S3 `github-pr-workflow` is conditional only for an authorized GitHub PR task and requires the adaptation described below. Feature-specific implementation skills are chosen from actually available project needs; none has been audited or mandated here. The prepared S5 common Council review protocol informs the submission contract when available but does not turn the Executor into its own reviewer.

**Authority.** May perform authorized changes, produce evidence, propose technical options and correct a justified gap. May not relax criteria, accept its own result, expand scope without mandate, create agents/skills by default, or infer external delivery permission. Submit through the native issue path under an intact review policy; a completion request is not itself Council acceptance. On an API error or assignment change, inspect the returned state and report the actual disposition. Native checkout is an execution mechanism, not permission to claim another agent's review stage.

### 3.2 Generalist Reviewer

**Mission and defended result.** Determine whether the current identified submission satisfies the request, relevant evidence and full mandate at proportionate cost. Defend usefulness, correctness and the essential journeys together. Choose a sufficient correction, reject an unjustified extension, or issue delegated acceptance. Reconcile product, architecture and quality concerns at a generalist level; seek a bounded specialist opinion only when needed.

**Required inputs.** Everything needed to compare result and mandate: the exact candidate and evidence identity, author, native review stage and current participant, owner decisions, prior objections/corrections, relevant source and user journey evidence, available usage/time observations and uncertainty. An unreadable artifact, missing decisive test or unmeasured decisive trade-off is not a pass.

**Trigger and stopping condition.** Start when Paperclip hands the review stage to this distinct identity. Read `executionState.currentParticipant`, `returnAssignee`, prior verdict and new evidence. Do not take an execution checkout merely to submit a review decision; the historical harness encountered a conflict doing so. Finish with one reasoned verdict and verified effect, one precise evidence/correction request, or an explicit owner-only waiting state. Re-review only the changed or newly uncertain parts and impacted criteria. Repetition without new evidence ends in a justified conclusion, blocker or escalation, not another identical pass.

**Observable output.** A concise record containing mandate/criteria, result and evidence identity, author/reviewer attribution, findings with consequences, accepted/dismissed objections, proposed outcome, permitted follow-up and owner-reserved questions. Record the native decision/application result separately from the reasoning verdict. For insufficient evidence say exactly what is missing and why it changes the decision. A favorable comment, CLI exit zero or successful test alone is not applied acceptance.

**Engine and access.** Shared contract: `codex_local`, explicit `cli`, WSL, proposed `gpt-5.6-sol` / `medium`, subscription authentication, bypass explicitly false. Native `role: "general"`, title `Generalist Reviewer`; `capabilities` describes review, evidence and mandate responsibilities. Read the same identified result the executor submitted, with task-relevant verification tools and the native review route. Tests may need disposable output; that does not authorize rewriting the submission. Effective write restrictions, tools, authentication and skill mounts remain unverified.

**Skills.** S1 `paperclip` required; S5 `council-review` is prepared as a reusable source and required as a mission contract when actually installed, selected and mounted. Until then, the autonomous minimum remains in the profile instructions. S2 `qa-acceptance` is conditional for feature/user-visible/release validation, after explicit adaptation. S4 `design-critique` is optional only if a concrete UI question is within this reviewer's competence; significant UX/accessibility questions may instead justify a V1 specialist. No full QA or design checklist is mandatory for every review.

**Authority and application.** May accept only a compliant identified result within the mandate; may request a minimal sufficient correction, reject a generic redesign without a justified need, and escalate reserved decisions. May not fix and approve the same changed candidate, overrule evidence by voting, or rewrite a human commitment. H1 proposes that this reviewer is both the accountable final verdict issuer and the active native review participant. V1 specialists contribute opinions; they do not independently close the governed issue.

The prototype's exact application path is `POST /api/plugins/<pluginId>/api/issues/<issueId>/decision`, with `approved` or `changes_requested`, a justification and `resultReference`. The plugin checks its configured Council identity and pending assignment, resolves its native secret reference, and calls public `PATCH /api/issues/<issueId>` under that identity/run. An approval requests `done`; a correction requests `in_progress`. Paperclip can instead advance to another stage or escalate to a human, so verify the returned issue and `executionState`, including the relevant decision, rather than trusting `requestedIssueStatus`. See [Local E6: worker, lines 35–68](#9-source-baseline-and-evidence-availability) and [native transition, lines 786–899](https://github.com/paperclipai/paperclip/blob/61b3fd57a695614dc4a37e2303f426a34a9795cf/server/src/services/issue-execution-policy.ts#L786).

For a mission already in N2, that endpoint returns HTTP 202 after persisting the
exact verdict as a prepared intent. The reviewer then finishes normally. The
`agent.run.finished` handler verifies the same reviewer/run/submission, waits a
bounded interval for authoritative usage, settles the review reservation, and
only then uses the same receipt-backed public PATCH. Missing events or unknown
usage leave the intent prepared; they do not authorize an alternate actor or a
manual resend.

The historical prototype does not enforce immutable result identity, the full mandate or interruption reconciliation. The separate manifest gate adds request/manifest/attachment-metadata checks; the TAD distinguishes those checks from complete content binding and recovery. These remain H1 work, not extra responsibilities solved by installing a skill. On uncertain application, preserve the verdict, read sufficient native state/history and reconcile before retry. On an owner-reserved question, save an appropriate human waiting path and recommendation; do not encode it as `approved`. Suspension must preserve pending work and the next action.

**Prepared common review protocol (S5).** A short reusable procedure is justified because every reviewer needs the same decision discipline:

1. Identify mandate, authority, current submission/evidence and the accountable verdict issuer; check that the author is distinct.
2. Review relevant criteria and consequences; distinguish supported facts, uncertainty, recommendations and decisions. Consult only the needed specialty.
3. Prefer the smallest sufficient correction; reuse evidence that remains valid. Each finding states the applicable criterion or risk, evidence and limits, concrete consequence, minimal correction or missing information, and class. Reject an unjustified technical extension without dropping an applicable obligation.
4. Produce one structured reasoning result: accept, request changes/evidence, or escalate/wait. Preserve original attributed specialist positions and visible dissent; dispose of objections without rewriting opinions or treating an absent required opinion as agreement. This is a conceptual output contract, not an invented native verdict enum. The prototype only accepts `approved` and `changes_requested`; waiting/escalation uses native human/dependency paths.
5. Apply only within mandate through the chosen integration, verify the actual effect, and preserve a resumable state on uncertainty. No prompt grants enforcement or broad key authority.
6. Stop when the result is accepted with confirmed effect, a precise correction is handed back, or an explained blocker/owner decision remains. Repeating unchanged evidence or exceeding the envelope does not authorize another loop.

Mission-specific expertise stays in instructions unless a repeated procedure or tool integration justifies another skill. Do not create one skill per title or a mandatory committee/review stack.

**Use operator-selected existing agents for V1.** Reuse appropriate existing identities and known WSL environments/authentication, then verify their distinct assignments, instructions, effective CLI settings, available evidence/tools and human destination.
